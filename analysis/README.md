# 소비 인텔리전스 · 데이터 분석 (포트폴리오)

'나만의 경제' 앱의 가계부 거래로
**① SQL로 소비 패턴을 분석**하고, **② 파이썬으로 이번 달 지출을 예측**하고, **③ 루미(AI)가 그 숫자를 쉬운 말로 설명**하는 기능을 만든 과정이다.
이 폴더는 배포 사이트에 올라가지 않는다(`.vercelignore`).

> 이 폴더의 데이터는 모두 **합성 데이터**(가상의 세 사람 × 13개월)다. 실제 개인정보는 쓰지 않았고,
> 결과 숫자는 *방법을 비교하는 용도*이며 실제 사람들의 소비 통계나 예측 성능이 아니다.

## 한눈에 보는 구조

```
                 ┌──────────────────────────── 휴대폰 (앱) ─────────────────────────────┐
 가계부 기록 ──▶ │ ledger.tx (localStorage · Firebase) ──읽기만──▶ METRICS 블록(index.html)  │
 (캡처·직접 기록)│                                                ├ 이번 달 현황 · 반복 결제 · 큰 지출 (SQL과 같은 규칙)
                 │                                                ├ 월말 예상 · 분류별 예상 · 예산 초과 가능성 (forecast.py B4와 같은 규칙)
                 │                                                └ 집계 숫자만 ──▶ /api/receipts (insight) ──▶ Gemini/OpenAI
                 │                                                                   └ 답의 숫자 검사 → 통과한 설명만 화면에
                 └───── 동의 후 CSV 내보내기 ─────────────────────────────────────────────┘
                                   │
                                   ▼  (내 컴퓨터)
        DuckDB SQL (analysis/sql) ─▶ 결과 CSV ─▶ 노트북(EDA·예측 비교) ─▶ 규칙·모델 선택
                                   │
            scripts/check-metrics.mjs: 같은 합성 데이터로 '앱 계산 = SQL·파이썬 결과'인지 자동 확인 (79개)
```

거래 기록이 각자의 휴대폰에만 있어 서버에서 SQL·모델을 돌리지 않는다. 대신 **SQL·파이썬을 '정답'으로 두고, 앱은 같은 규칙을 자바스크립트로 계산**한 뒤 결과가 같은지 테스트로 묶었다.

## 1단계 · SQL 소비 분석

| 쿼리 | 무엇을 | SQL 기술 |
| --- | --- | --- |
| `01_monthly_summary` | 월별 쓴 돈·수입·고정/변동, 증감률 | CTE, `FILTER` 조건부 집계, `LAG` |
| `02_category_trend` | 분류별 월 지출·비중·증감률·3개월 이동평균 | 사람×달×분류 격자 JOIN(0원 달 채우기), 윈도우 |
| `03_weekday` | 요일별 하루 평균 변동비 | `generate_series` 달력 + `LEFT JOIN` |
| `04_fixed_variable` | 고정비·변동비 비중 | `JOIN`, 상관 서브쿼리, `string_agg` |
| `05_recurring` | 반복 결제 탐지 | `LAG`로 간격, `median`·`stddev_pop` |
| `06_anomaly` | 평소보다 큰 지출 | 날짜 범위 윈도우 `RANGE … PRECEDING`, `quantile_cont` |
| `07_budget` | 예산 대비 지출 | `LEFT JOIN`, `CASE` |
| `08_month_to_date` | 이번 달 vs 지난달 같은 기간 | 날짜 계산, `GROUPING SETS` |

**이상 지출 규칙을 데이터로 고침** (정답 5건)

| 규칙 | 잡은 수 | 맞힘 | 정밀도 | 재현율 |
| --- | --- | --- | --- | --- |
| A 중앙값 + 3.5×MAD | 140 | 4 | 0.03 | 0.8 |
| **B P95 × 2 (앱)** | 7 | 4 | 0.57 | 0.8 |

식비 안에 '구내식당 1만원'과 '배달 2~5만원'이 섞인 두 봉우리 분포 때문에 A는 평범한 배달까지 잡았다. B는 기록이 적은 분류를 놓친다(콜드 스타트).

## 2단계 · 이번 달 지출 예측

**문제**: c일까지의 가계부로 이번 달 전체 '쓴 돈'을 맞힌다. 사람 × 다 끝난 달 × c(1~말일−1) = 학습 525줄 · 검증 357줄.
**검증**: 달 단위 시간 순서 — 2026-01~06 학습, 07~10 검증. 같은 달을 학습·검증에 나누지 않는다.
**지표**: MAE(평균 몇 원 틀렸나) · 보조로 MAPE.

| 모델 | MAE | 1~10일 | 11~20일 | 21일~ |
| --- | --- | --- | --- | --- |
| B1 진행 속도 | 145,564 | 278,831 | 115,806 | 39,403 |
| B2 최근 3달 평균 | 161,679 | 161,796 | 161,796 | 161,439 |
| B3 최근 28일 속도 | 86,235 | 137,171 | 84,531 | 35,739 |
| **B4 혼합 (앱)** | **83,776** | 137,008 | 83,187 | **29,782** |
| Ridge | 101,354 | 121,105 | 101,370 | 81,079 |
| XGBoost | 109,963 | 122,500 | 104,796 | 102,402 |

**처음 보는 사람 검증**(두 사람으로 학습 → 남은 한 사람): B4 평균 MAE 83,776원, Ridge·XGBoost는 41만~127만원으로 크게 틀렸다. 사람마다 고정비·소비 수준이 달라 두 사람으로 배운 관계가 세 번째에 맞지 않는다.

**→ 앱은 B4 혼합**(지난 날 비율만큼 '최근 28일 속도', 남은 날 비율만큼 '최근 3달 평균'. 3달 기록이 없으면 B3). 기록이 28일보다 짧으면 숫자 대신 안내만 보여 준다.

### 미래 정보 누수를 찾고 고친 기록
처음엔 Ridge MAE가 **8,553원(1.3%)**으로 비현실적으로 좋았다. '지난달 쓴 돈' 특징을 정답과 직접 비교하니 **차이가 0원** — 날짜 오프셋(`prev_end - MonthBegin(0)`)이 이번 달 1일로 넘어가 **이번 달 정답이 특징에 들어가 있었다.** 달 번호(Period)로 명시적으로 계산해 고쳤고, 고친 뒤 머신러닝은 기준 모델보다 나빠졌다. *너무 좋은 결과는 먼저 의심한다.*

### 변수 중요도 (원인이 아니다)
XGBoost gain 1위는 `fixed_month`(한 달 고정비 합계, 93%)였다. 사람마다 달라 사실상 **'누구인지'를 알려 주는 신호**로 쓰였다는 뜻이고, '고정비가 지출을 늘린다'는 인과가 아니다. 순열 중요도(검증 데이터에서 섞었을 때 MAE 증가)도 함께 보고, 앱에는 중요도 대신 '지난달 같은 기간보다 가장 많이 늘어난 분류'처럼 확실한 계산을 보여 준다.

### 예산 초과 가능성
최근 84일에서 '남은 날 수만큼 이어진 기간'의 변동비 합을 하나씩 대입해 예산을 넘는 비율을 센다(같은 입력이면 같은 값 → 앱과 똑같이 계산). 검증 달 15일 시점 Brier 점수 **0.122** (늘 같은 확률을 말할 때 0.188보다 좋음).

### 이상 패턴: 규칙 vs IsolationForest
IsolationForest 상위 5건은 정답 5건을 모두 맞혔지만, ① 전체 기간(그 거래 이후 포함)으로 특징을 만들었고 ② '몇 건'인지 미리 알아야 한다. 앱 알림은 그날 기록만으로 이유를 말해야 해서 규칙(P95×2)을 쓰고, IsolationForest는 '지난달 돌아보기' 리포트 후보로 남긴다.

## 3단계 · 루미 AI 인사이트

- **역할 분리**: 숫자는 앱이 계산(1·2단계 규칙), AI는 설명만. 앱은 계산한 숫자만 묶어(`insightFacts`) 보내고, 서버(`cleanFacts`)가 정해진 칸만 남긴다 — 가게 이름·개별 거래는 보내지 않는다.
- **숫자 검사**(`numbersOk`): AI 답에서 숫자(만원·원·%·일·번…)를 모두 꺼내 facts에 있는 값인지 확인한다. 하나라도 없으면 그 답은 버리고 횟수도 차감하지 않으며, 앱이 같은 숫자로 만든 '계산한 요약' 문장을 보여 준다.
- **재사용**: `api/_ai.js`(Gemini 무료 등급 → 실패 시 OpenAI), 루미의 피드백 주 3번 한도·광고 보상, 첫 사용 시 동의.
- 테스트(`scripts/check-insight.mjs`): 정상 답 통과 · 지어낸 숫자(35%, 9만원) 차단 · 가게 이름이 AI로 가지 않음 · 숫자 없으면 AI를 부르지 않음.

## 기술을 고른 이유 (면접용 요약)

| 결정 | 이유 | 다른 선택지 |
| --- | --- | --- |
| DuckDB | 서버 없이 도는 분석용 SQL. CSV 직접 읽기, 윈도우·`median`·`quantile_cont`. 무료 | SQLite(분석 함수 부족), PostgreSQL(서버·권한·비용·Firebase 이중 저장) |
| 로버스트 통계(중앙값·P95) | 큰 지출 한두 번에 '평소'가 끌려가지 않게 | 평균·표준편차 |
| 기준 모델 먼저 | 데이터가 적으면 복잡한 모델이 외우기 쉽다. '단순한 것보다 나은가'를 증명해야 쓸 이유가 생김 | 처음부터 XGBoost |
| 시간 순서 검증 + 새 사람 검증 | 미래 정보 누수 방지, 새 사용자에게 통하는지 확인 | 무작위 분할(성능 부풀림) |
| MAE | '평균 몇 원 틀렸나'라 해석이 쉬움 | MAPE(작은 값에서 튐) |
| 앱은 휴대폰 안에서 계산 | 개인정보가 밖으로 안 나가고 무료 | 파이썬 API(요약을 매번 서버로, 큰 라이브러리 크기·느린 시작) |
| AI는 설명만 + 숫자 검사 | LLM이 숫자를 지어내지 못하게 | AI에게 계산까지 맡기기 |

## 한계

- 합성 데이터는 실제보다 규칙적이고, 규칙을 만든 사람이 만든 데이터라 규칙이 데이터에 맞춰질 위험이 있다 → 동의받은 실제 데이터로 다시 확인해야 한다.
- 학습할 사람이 3명뿐이라 머신러닝 비교 결과는 '이 크기에서는'이라는 조건이 붙는다. 실제 데이터가 충분히 모이면 같은 코드로 다시 비교한다.
- 분류는 사용자가 고른 값이라 틀릴 수 있다. 예측은 '추정'으로 표시한다.
- 앱의 Firebase 동기화는 계정 문서 하나를 통째로 덮어쓰는 방식이라(기존 구조), 새 기능은 거래를 읽기만 해서 이 위험을 키우지 않게 했다.
